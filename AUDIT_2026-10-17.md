## Confirmed issues and design backlog

### 1. Workflow shortcuts do not open the intended accounting form

Priority: high, functional navigation bug.

- `components/owner/workflows.tsx:15`: **Create invoice** links to `/accounting?create=1`.
- `app/(dashboard)/accounting/page.tsx:132`: the page opens its create dialog only when `create=invoice`.
- Result: the workflow shortcut loads Accounting without opening the invoice form.
- `components/owner/workflows.tsx:19`: **Record expense** also uses `?create=1`, which the same handler ignores. **Upload receipt** and **Send payment reminder** both link only to `/accounting`, with no command-specific state.
- Required work: agree on accepted URL actions, open the correct form/type, and provide actual receipt/reminder flows if retained as active workflow cards. These are source-confirmed mismatches; browser reproduction in the owner application is pending.

### 3. Global Settings security, accounts and billing are partial relative to the PDF

Priority: high for missing capability; medium for layout.

- **p.325 Active Sessions:** no per-device registry, device/session list or single-device revocation. Current UI shows session information and revoke-all. See `settings-page.tsx:198–212` and backend `businessOwnerSettings.controller.js:80`.
- **p.326 MFA:** authenticator setup/verification exists, but uses a manual secret rather than the reference QR presentation; recovery codes are explicitly unsupported.
- **p.327 Connected Accounts:** Gmail connection exists. Outlook is explicitly unavailable in this owner flow; social sign-in is also unavailable. Do not infer Outlook completion merely from its init route.
- **p.332 Payment method:** Manage payment method opens the provider billing portal; the reference in-app payment-method modal is absent. This is a valid alternate provider flow, but not the reference design.
- **p.333–340 preference screens:** many use the same two-column `PreferenceForm`, without all the individual reference status cards/summary panels. Notification quiet-hours preferences are saved but not enforced by delivery.
- Billing history invoice download currently exports a JSON invoice record. Provider-issued documents are delegated to the billing portal.

### 4. Live View and Supporter cannot perform live provider actions yet

Priority: high, backend integration.

- `../backendKoraAi/controller/businessLive.controller.js` returns `callControlAvailable: false`.
- `components/owner/live-view.tsx:50` renders transcript detail and says live audio controls are unavailable. Internal notes, flags and handover tasks are implemented; these do not join, mute or take over a call.
- `../backendKoraAi/controller/businessSupporter.controller.js:29` reports `deployment.available: false`, and publication saves desired configuration without applying it to a provider.
- Required work: supported provider adapters, deployment/acknowledgment/error state, real preview/test actions and verified incoming/outgoing channel behavior. Do not count successful configuration persistence as live activation.

### 5. Inbox capability gaps

Priority: medium.

- `components/owner/inbox-email.tsx:46`: Scheduled folder is disabled because email scheduling is not configured.
- Gmail archive/trash/star/label/snooze controls are disabled or delegated to Gmail; only NOVYA-local mailbox actions are handled in-app. Gmail sent history and some attachments remain provider-side.
- Personal chat pins/notes use browser storage rather than server persistence. They do not synchronize across devices.
- Required work if full mailbox behavior is expected: scheduled delivery worker, provider mailbox operations/files/history and server-side personal metadata.

### 7. Backend settings capabilities and enforcement still missing

Priority: high for operational completeness.

`../backendKoraAi/controller/businessOwnerSettings.controller.js:80` explicitly marks these unavailable: `oauthSignIn`, `perDeviceSessions`, `ownerApiKeys`, `outboundWebhooks`, `retentionWorker`.

`../backendKoraAi/utils/businessOwnerSettings.js` also documents that quiet hours, retry defaults, retention/residency requirements and several module/approval defaults are stored preferences, not implementations of the corresponding infrastructure. Existing operational endpoints continue to enforce their own rules.

Distinguish these backend gaps from merely configuring secrets: several require new services/adapters/workers, not only `.env` values. Existing Gmail/MFA/Stripe code should instead be verified against actual configured providers before declaring live completion.
